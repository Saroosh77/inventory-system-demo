# Inventory & Invoicing — live demo

A working demonstration of the inventory, invoicing and financial-reporting
core of an ERP built for food distribution: multi-warehouse stock control with
batch and expiry tracking, a GST/non-GST sales invoice register, a
double-entry general ledger behind the P&L, trial balance and balance sheet,
and role-secured master data administration.

**Everything in this demo is fictional.** The company, the products, the
customers, the staff and every figure are generated by `prisma/seed.ts`.

## Sign in

Three accounts are seeded, one per role. They are listed on the sign-in screen
and fill the form in one click — the point of the demo is to sign in as each
and watch the application show you less.

| Account | Role | What this role can reach |
| --- | --- | --- |
| `admin@demo.local` | Administrator | Every module, including master data and user management |
| `finance@demo.local` | Finance | Invoices, P&L, ledger, stock and costs — but no master data or user management |
| `warehouse@demo.local` | Warehouse | Its own warehouse's stock only: no costs, no margins, no invoices |

All three share the password in `DEMO_USER_PASSWORD` (`DemoPass!2026` by
default).

Worth trying: sign in as **Warehouse**, then as **Finance**. Item costs, stock
valuation, salaries, gross profit and the entire invoice register disappear —
and not just from the screen. The API response for the warehouse role does not
contain those fields at all.

## Technical highlights

- **Authorization is enforced at the service and data layer, not the UI.**
  Every module entry point calls `assertPermission` before it queries, and
  cost, salary and margin fields are masked inside the query result
  (`lib/server/modules/workspace/workspace-service.ts`) rather than hidden in
  the component. Hiding a nav item is not access control; the payload a role
  receives is the boundary.
- **Append-only stock ledger with a balance projection.** Stock is never
  mutated in place. Every movement is an immutable `StockMovement` row, and
  `StockBalance` is a projection updated in the same transaction
  (`lib/server/modules/inventory/stock-ledger.ts`), guarded by a database
  CHECK constraint so no path can drive a balance negative. Batches are
  consumed FIFO by expiry date.
- **Double-entry general ledger.** Invoices, recoveries and stock adjustments
  post balanced journal entries through a single `postJournalEntry` function
  that refuses an out-of-balance entry, so the trial balance and balance sheet
  are derived from the ledger rather than recomputed from documents.
  Cancelling an invoice reverses its entry instead of deleting it.
- **Session authentication with sliding expiry.** Opaque tokens are stored
  hashed, the session slides forward on use up to an absolute ceiling, and
  sign-in is rate-limited per identifier
  (`lib/server/auth/`).
- **Hardened headers.** Per-request CSP with a nonce and `strict-dynamic`
  (no `unsafe-inline` scripts), plus HSTS, `X-Frame-Options: DENY` and
  `frame-ancestors 'none'` — see `proxy.ts` and `next.config.ts`.

## Domain rules the demo shows

- A distributor's onward resale (a *secondary* sale) is that distributor's
  revenue, not the company's. It is tracked and reported, but excluded from
  company P&L and never reaches the company general ledger — otherwise the
  same goods would be booked as revenue twice.
- Distributor warehouses hold finished goods only, and their stock is not a
  company asset, so an adjustment there has no company ledger effect.
- Document numbers are allocated per year (`INV-2026-00001`), so each year is
  its own contiguous, auditable series.

## Running it locally

Requires Docker and Node 22+.

```bash
cp .env.example .env
npm install
npm run demo:up     # starts Postgres, applies migrations, loads the demo data
npm run dev
```

Then open http://localhost:3000.

Useful scripts:

| Command | Does |
| --- | --- |
| `npm run db:seed` | Wipes and regenerates the demo data set |
| `npm run db:reset` | Drops the schema, re-migrates, re-seeds |
| `npm run check` | Lint, typecheck, tests and a production build |
| `npm run db:studio` | Prisma Studio against the demo database |

## About the demo data

`prisma/seed.ts` generates roughly four months of trading backwards from the
day it runs, so the demo never looks stale: ~160 invoices across the three
sales channels, recoveries in cash, bank, cheque and online, stock transfers
between warehouses, write-offs and count corrections, and a national city
reference table. It is deterministic — a fixed-seed generator, so every run
produces the same figures — and internally consistent: stock moves through the
same primitives the application uses, so the trial balance balances and the
balance sheet ties out.

Because anyone signing in as the administrator can edit or delete records,
`.github/workflows/reseed.yml` restores the data set daily.
